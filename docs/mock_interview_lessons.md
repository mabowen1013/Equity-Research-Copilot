## 0. 贯穿全程的主线（最重要）

今天 7 道题，本质在反复训练同一个成熟度：

1. **精确划定"我保证了什么 / 没保证什么"。** 别吹"我防住了一切幻觉 / 我的 eval 证明答案正确"。能划清边界，比漂亮的 pass_rate 唬人得多。
2. **把功劳归因到真正命中瓶颈的地方。** 先测量（你有 `timing_ms`），再优化最长那根杆。
3. **能为合理的设计决策据理力争，而不是被一推就折。** 折叠 = 显得对自己项目没想清楚。

要改掉的三个习惯：
- ❌ 遇到难题说"等以后优化代码再解决"——面试里 = 当场出局。任何决策都要能讲取舍。
- ❌ 讲流程讲到"生成答案"就停手，反复漏掉**引用校验**（你的第二个简历卖点）。
- ❌ 凭感觉/挑好做的地方优化（HNSW），而不是 profile 后打长杆。

## 1. 这个 agent 到底是什么

**陷阱问题：** "你简历写 ReAct agent，但代码是 if/elif 规则，它还算 agent 吗？"

**诚实答案：** 它是**有界的、规则驱动的 ReAct 式控制器**——一个状态机。LLM 只在进循环**之前**做 planning；循环内部一步 LLM 都不调，靠"证据充分性 flags"判断走到哪。Agentic 的部分是 `plan→act→observe→重判充分性→动态停止` 这个**闭环**，以及条件式后续动作（MD&A 不够→自动转分部讨论）。它**不是** router：router 一次性分发、不看结果；它会"看了上一步结果再决定下一步"。

**机制要点：**
- 6 个工具分两族：`query_xbrl_metrics`（回**结构化数字**，不走向量检索）；`retrieve_*`（回 **chunk**，每个工具**在自己角色范围内各跑一遍** dense+lexical+RRF+rerank）。
- 结果累积进 accumulator，**evidence pack 每步重建**用来判断充分性。
- 停止条件：证据充分 / `max_steps`(=5) / 无有用动作（insufficient_evidence）。

**30 秒话术：**
> "LLM 先出 JSON 槽位；然后进一个有界规则 ReAct 循环：每轮 if/elif 选一个检索工具，XBRL 工具回结构化数字、文本工具在各自角色范围内跑 dense+lexical+RRF+rerank 回 chunk，结果累积并重建 evidence pack，用角色覆盖判断够不够——够则停、生成**带引用**的答案、过校验，不够则按缺口选下一个工具。工具选择是规则而非 LLM，是为延迟和可评估性做的有意取舍。"

## 2. 为什么不让 LLM 自己选工具

**陷阱问题：** "业界都用 LLM function-calling，你为什么用死规则？"

**论证（4 轴，每个都带代价）：**
| 轴 | 规则赢在哪 | 代价 |
|---|---|---|
| 延迟/成本 | LLM 选工具=循环每步多一次串行 LLM 调用（最多 5 次）；瓶颈本就是 LLM | 零适应性 |
| 确定性/可测试 | `(plan,flags)→动作` 纯函数，每步可单测可回归 | 死板 |
| 领域特性 | 小而封闭的决策空间（固定指标+章节+6工具） | taxonomy 外问法静默降级 |
| 失败模式 | 最坏=证据弱→说不足，**有界** | 质量上限低 |

**何时该换 LLM（满分加分项）：** 问题空间不可枚举（跨公司/多步分析）、内容驱动的多跳、工具爆炸时。务实方案=80% 规则 + 长尾 LLM。

**两个高级反击：**
- 被问"你 planner 不也用 LLM、不也不确定？"→ **"原则不是避免 LLM，是控制不确定性的注入点：planner 注入一次、当场 schema 校验、可缓存，且给定 plan 后下游全确定；每步选工具会注入 5 次、不可校验、不可缓存、还复利传播。"**
- 别把"小封闭空间"说成"项目简单"。说成 **"v1 刻意收窄决策空间以先打透确定性/可审计，这是有意的工程边界、不是领域天花板；v2 扩到开放式多跳时正好触发换 LLM。"** 别为了"显得高级"而加 LLM（resume-driven development，面试官闻得出来）。

## 3. 引用校验 / 反幻觉（核心安全卖点）

**陷阱场景：** 模型生成"Apple 将停产 iPhone `[3]`"（纯编造，但 `[3]` 是合法证据）——会 passed 还是 failed？

**诚实答案：会 passed，连 warning 都没有。**
- 硬性 fail 只有两种：空答案 / 没有任何合法引用。
- 数字对账只对**编造的数字**报 **warning**（不 block）；这句没数字 → 不触发。带合法 marker → 连 uncited 警告都没有。

**一句话点破：**
> **校验验的是「引用完整性」（指针指向真实证据），不是「语义蕴含」（证据是否真的支持这句话）。我建好了第一种，没建第二种。**

**话术（划边界）：**
> "我提供两个可审计硬保证：①每个引用都指向真实证据；②每个金融数字都和证据在容差内对过账。我**没有**提供 claim 级语义蕴含校验——不带数字的编造结论配合法引用会被放过。这是我清楚的边界，下一步就是补它。"

**怎么补：** 答案拆原子 claim → 对所引证据做蕴含判断（NLI / LLM-judge over cited span）→ contradict/neutral 拦或降级。

## 4. 流式输出的"先展示后撤回"

**陷阱问题：** 流式逐字蹦出的是**校验前**草稿，最后整体替换——投研场景可接受吗？

**诚实答案：不可接受。** 会被判 failed 的答案（甚至幻觉），在被拦下前用户已经一个字一个字读到了，可能已截图。

**修法（把"展示活跃度"和"展示答案"解耦）：**
1. **流 agent 进度、不流答案草稿**（你已经在发 status/step 事件，去掉 answer_delta，答案校验后在 run 事件揭晓）——最推荐。
2. **无证据情况生成前短路**（`prompt_evidence_ids` 为空就别启动答案 LLM）。
3. 退一步：句级 holdback 校验，或显式标"草稿·校验中"再过渡。

**话术：**
> "我发现流式把校验前草稿推给用户、再整体替换，是不可接受的'先展示后撤回'。修法是解耦'展示活跃度'和'展示答案'：用已有的进度事件撑活跃感，答案正文校验通过后再揭晓，并对无证据情况在生成前短路。这样既保留低感知延迟，又保证用户看到的每个字都过了安全闸门。"

## 5. 评估（eval）：验形状还是验对错

**陷阱场景：** 答案把营收编成 $999B（真值 ~$95B），能过 `aapl_latest_quarter_revenue` 用例吗？

**诚实答案：能过，绿的。** `must_match` 只验 `\$\d`（有个美元数字），不验数值对错；`unsupported_number` warning 存在但 **eval 的 `check_case` 根本不读 warning**——它对 eval 隐形。

**一句话：**
> **answer eval 验的是「形状」（格式合规/带引用/够快/无投资建议），不是「对错」。** 全绿只证明"产出格式良好、安全、带引用、够快的答案"，**不证明答案正确**。

**另两道裂缝：** ①5 条用例全 AAPL，零泛化信号；②gold 证据 id 从自身检索 dump"反向种"出来，只能抓回归、永远没法说系统一开始就错了。

**便宜的补法：** warning 进 gate（对 `unsupported_number` 失败）；`must_match` 断言真实数值；独立标注 + 跨 ticker gold 集。

## 6. 并发与线程安全（流式端点）

**为什么把 run 丢进 `run_in_executor` 线程？** 因为 `ResearchRunService.run()` 是**同步阻塞**的（阻塞式 LLM/DB 调用，不 await）。直接在 async handler 里跑会**卡死单线程 event loop ~15s**，期间所有其他请求（连 /health）全冻住。丢进线程池，event loop 才能继续让出、服务别人。

**为什么 emit 用 `call_soon_threadsafe`？** `asyncio.Queue` **不是线程安全**的，只能被 event loop 线程碰。worker 在别的线程，必须用 `call_soon_threadsafe` 把 `put_nowait` 调度回 loop 线程执行。这是 asyncio 唯一允许跨线程调用的 API，写法是对的。

**Session 线程安全（题目隐藏点）：** `db` 在请求里建、却在 worker 线程用。SQLAlchemy Session 非线程安全，但**实践中不出错**因为访问被限制在唯一一个 worker 线程（event loop 只碰 queue）。**但很脆**——没东西强制这个限制。

**断连会怎样？** worker **不会停**：Python 杀不掉运行中的线程，`run_in_executor` 不传播取消。LLM 继续烧 token、`persist_run` 照样写一条没人看的 run。

**扩展天花板：** 每路流钉住一个线程池线程 + 一个 DB 连接整整 ~15s，~100 并发就榨干两个池。要规模化得换异步执行模型或任务队列（Celery/RQ/arq）。

**话术：** 见正文末尾的 6 号话术（丢线程的原因 + call_soon_threadsafe + 两个已知短板：断连不取消、每路钉住线程+连接）。

## 7. 延迟优化：优化对地方了吗

**数据：** 冷 ~19s / 暖 ~6.6s，**其中检索仅 92ms**。瓶颈是**答案 LLM 一个字一个字解码**。冷暖 ~12s 差 = planner LLM + embedding 未命中缓存的额外串行往返。

**铁律：** **LLM 生成延迟主要由「输出 token 数」决定**——解码是串行的；prefill 便宜，decode 是长杆。

**真·延迟杠杆：**
| 杠杆 | 你做了吗 |
|---|---|
| ①减少输出 token（`ANSWER_LLM_MAX_OUTPUT_TOKENS`+句数限制） | ✅ **真正命中瓶颈的优化** |
| ②更快/更小模型（分层） | ❌ |
| ③砍关键路径串行 LLM 调用（planner+rewriter 合并） | ✅ 命中 |
| ④减少重试（失败要重跑整次，尾延迟翻倍） | ❌ |
| ⑤provider prompt caching | ❌ |
| 流式 | ✅ 但**只降感知延迟、不降 wall-clock** |

**HNSW 的诚实归因：** 2254 条向量上建 HNSW 省的延迟≈0（flat 搜索本就百毫秒级）——这是**对着非瓶颈优化**。它在百万级才正确。**简历/叙事里把它归为"扩展准备"，不是"延迟优化"**，否则被问"省了多少 ms"就崩。

**元 lesson：** 先看 `timing_ms`/`duration_ms` 找长杆，再动手。别挑"有意思/好做"的地方优化。
